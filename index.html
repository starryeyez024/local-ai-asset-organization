A methodology for AI tooling hygiene

One Root, No Duplicates

A general approach for organizing AI agent skills and MCP servers so they have a single source of truth on disk, stay in sync across every tool that reads them, and never get silently duplicated, broken, or overwritten when something moves.

One physical root, symlinked everywhere

Summary

The whole approach in five moves

Move What it solves
1)Flatten One physical root, one entry per repo, named from the git remote — eliminates "which copy is real" and folder-name-vs-owner mismatches.
2)Symlink One canonical hub directory (e.g. ~/.agents/skills) holds the real per-repo symlinks; every other tool points a single symlink at that hub instead of rebuilding its own — moving or renaming touches symlinks only, never file contents.
3)Split MCP Real code checkouts get a folder entry; doc-only servers get a lone file — and a stable indirection symlink absorbs future path changes for hardcoded configs.
4)Override safely Copy → edit → re-point instead of editing vendor/team skills in place, backed by a real, downloadable agent-facing safeguard skill as defense-in-depth.
5)Match tooling to mechanism Know whether each tool discovers or is configured, and whether each installer copies or understands symlinks, before trusting it near the new layout.

The problem

AI assets sprawl across every tool you install

Once you use more than one AI coding tool, the same category of asset — a reusable skill, an MCP server checkout — ends up scattered across several tool-specific directories, each with its own installer, its own naming habits, and its own idea of where things should live.

In practice this shows up as a predictable list of symptoms:

The scattered starting point this methodology fixes

  • No single source of truth. The same skill might exist as a real directory in one tool's folder, a copy tracked by a different tool's installer, and a symlink somewhere else — three different "current" versions with no way to tell which one is authoritative.
  • Symlinks that break on a move. A symlink points at an absolute path. Rename or relocate the folder it targets — even for an unrelated reason — and every symlink pointing at it silently goes dark.
  • Finder-style aliases masquerading as symlinks. On macOS in particular, it's easy to end up with alias files instead of real symlinks. They look identical in a folder listing, but no command-line tool or agent runtime follows them.
  • Drift against git remotes. Once copies and symlinks are mixed together across tools, it becomes unclear which physical location is safe to git pull or edit, and which is a derived copy that will get silently overwritten or left stale.

None of this is caused by any one tool doing something wrong. It's the natural result of independent tools each shipping their own convention for "where skills live," with no shared layer underneath them.

The architecture

One physical root, one canonical hub, and symlink views

The fix is architectural, not procedural: pick exactly one folder on disk that is the real physical home for every AI repository you use. Everywhere else a tool expects to find these assets becomes a symlink pointing back into this structure, never a second copy.

Physical root vs. tool-facing symlink views

~/AI Assets/ — real files live here, once

@org-a--repo-one/
@org-b--repo-two/
└── skills/
    └── example-skill-name/
        └── SKILL.md
@platform-org--build-automation/
↓ symlinked into every tool's directory

~/.agents/skills/ — the canonical hub: every skill's symlink is listed here by name, once

repo-one                   → ~/AI Assets/@org-a--repo-one/
example-skill-name         → ~/AI Assets/@org-b--repo-two/skills/example-skill-name/
build-automation           → ~/AI Assets/@platform-org--build-automation/

~/.codeassist-ide/skills — a second tool, collapsed to one symlink pointing at the hub

skills                     → ~/.agents/skills

Every line in the top panel is a symlink; the physical root above is the only place real files exist. ~/.agents/skills is the one canonical hub folder holding all of those per-repo symlinks — every other tool directory is a single symlink pointing at the hub.

What if two different repos ship the same skill name?

Say @org-a--repo-one and @org-b--repo-two each contain a skill folder literally named example-skill-name. A flat hub can only ever point one name at one target.

Fix it at the source by renaming the skill folder in whichever repo you control, or pick which one keeps the plain name in the hub. If you need both live at once, symlink the second under an org-prefixed name (e.g. org-b--example-skill-name). Any tooling that builds the hub should warn and skip on collisions rather than silently overwriting.

Physical Root & Identity

Organize however you like — just derive names from the git remote

Use nested org directories /org-name/repo-name/ or an @org-- prefix, pick whatever is easiest to scan for you!

Gotcha: Container folder names can be mismatched with the actual git remote

Local folder names reflect where someone cloned a repo, not who owns the code:

  • Local path on disk: team-a-tools/internal-tools-cli
  • Actual Git remote: git@example.com:platform-org/internal-tools-cli.git
  • Correct flat entry: @platform-org--internal-tools-cli

What about custom homemade skills?

If there is no remote to derive a name from, simply prefix it with a default namespace (@personal--).

MCP servers

Two kinds of MCP server need two different treatments

MCP servers are configured via explicit file paths rather than scanned directories. Because config files hardcode exact paths, a stable indirection symlink layer is critical to prevent path breakage when a repository reorganizes.

Real local code checkout

Local code, virtual environments, or launch scripts get a normal flat physical entry in the root (@vendor-org--example-mcp-server/).

Documentation-only / vendor-hosted

Remote URLs or globally installed binaries get a lone symlinked markdown file at the root's top level (@acme-team--docs-mcp.md), avoiding unnecessary folder overhead.

The override problem

Never edit a vendor or team skill in place

Editing a shared or vendor skill directly inside its source repo creates uncommitted drift that gets overwritten on the next git pull.

Copy → edit → re-point

  1. Copy the whole skill folder into a dedicated overrides area of the physical root.
  2. Make your edits in the copy. The original upstream folder is left untouched.
  3. Re-point the single tool-facing hub symlink for that skill's name at the new override location.

Concrete example: a skill after being overridden

~/AI Assets/ — vendor original untouched, override copy added alongside it

@org-a--fiddlewidget/
@personal--fiddlewidget/
└── skills/
    └── fiddlewidget/
        └── SKILL.md

~/.agents/skills/ — the tool-facing symlink re-pointed off the vendor copy

fiddlewidget               → ~/AI Assets/@personal--fiddlewidget/skills/fiddlewidget/

Tooling & Case Studies

Bridging copy-based tools like Lola with the hub

Many skill package managers are copy-based: installing writes a fresh copy straight into the destination directory without recognizing symlinks.

Case Study: Lola (AI Skills Package Manager CLI)

lola install writes a fresh copy of each skill into a tool's skill folder (e.g. ~/.claude/skills/<skill>/). If a symlink already exists there, it unlinks it and converts it back into an unlinked copy.

To bridge this gap until native symlink resolution exists, this repository carries a bridge script: scripts/lola-post-install-hub-bridge.sh.

Triggered after installation, it moves newly-copied skill folders into ~/AI Assets/@lola--<module-name>/<skill-name>/ and replaces the original path with a symlink back to the hub. 

lola install my-module ./my-project -a claude-code -s user \
  --post-install "$HOME/AI Assets/@ktotten--local-ai-asset-organization/scripts/lola-post-install-hub-bridge.sh"
