What this is

A local, filterable browser for the AI skills installed on this machine. It has two views: Browse Skills — a curated, filterable catalog of the ixd-firefly "AI-first" skills across 6 persona modules (Product Management, Program Management, Data Science, UX Design, UX Research, Content Creation) — and Maintain Skills — a raw audit of everything in your local skills folder, including skills outside that curated set, broken symlinks, duplicates, and stale definitions.

How the data is built

Nothing in this tool is dynamic or AI-generated at browse time. A Python script, generate-skills-json.py, runs once (whenever you tell it to — see "Refreshing the data" below) and writes a single static file, skills.json. index.html just does one fetch("skills.json") on page load and renders everything from that. There's no server-side logic, no database, no live re-scanning while you browse.

The script's actual steps:

  1. Walk ~/.agents/skills (a flat, symlink-only folder — the same list Cursor and Codex CLI read natively; override with the SKILLS_ROOT env var).
  2. Resolve each entry to its real target folder and look for a SKILL.md file.
  3. Parse that file's YAML frontmatter (name, description, metadata.skill-type, etc.) plus a few specific markdown sections in the body — ## Inputs, ## Trigger / ## When to Use, and ## Required skills — using regex-based parsing (no AI, no LLM calls).
  4. Run every skill's name + description + first ~1000 characters of body text through several keyword-matching functions (below) to assign tags.
  5. If the resolved folder belongs to one of the 6 known ixd-firefly modules, add it to the curated skills array (this is what Browse Skills shows). Every farm entry — curated or not, broken or not — also goes into a separate inventory array (this is what Maintain Skills shows).

How tags get assigned (and why you might disagree with one)

Every tag on every skill is a keyword-regex guess, not a judgment call by a person or an AI. The script scans each skill's name, description, and the start of its body text for pattern matches against fixed keyword lists, and assigns whichever tags match. There's no semantic understanding involved — if a skill's description happens to contain the word "plan," it can pick up a Planning-flavored tag even if the skill isn't really about planning. This is exactly why you'll sometimes look at a skill's tags and think "that's not right."

Tag groupExampleHow it's decided
Tool jira, confluence, figma, slack, git... Keyword match per tool (e.g. "jira" tag fires on jira, epic, sprint, backlog, etc.). A skill can get multiple tool tags.
Role product-manager, ux-designer... Fixed 1:1 mapping from which of the 6 ixd-firefly modules the skill's real folder lives under — not keyword-based, this one's reliable.
Task Type planning, analysis, generation, validation, reporting... 12 keyword buckets (e.g. "generation" fires on generat, draft, create, author, write). A skill can match several buckets at once.
Skill Type Workflow / Atomic Reads metadata.skill-type from frontmatter if present; otherwise guesses "workflow" if the skill's id starts with workflow-.
Agile Phase Planning / In Progress / Retrospective Checked in priority order — retrospective keywords (retro, baseline, trend...) win first, then planning keywords (roadmap, capacity, backlog...), and everything else defaults to "In Progress" even if nothing matched. This is the tag most likely to feel wrong, since it's a single guess picked from a short priority list, not a real classification.
Work Stage Gather / Produce / Reflect Same idea as Agile Phase — keyword buckets for "gather" (ingest, discover, research...), "produce" (generate, analyze, validate...), "reflect" (retro, baseline, historical...). Workflows additionally inherit every stage tag of the atomic skills they call.
So if you see 4 skills tagged "In Progress" that you'd actually call "Planning": that's the keyword lists not covering the words those particular skills happen to use — it's not a bug you can fix by clicking anything in the UI today. The only way to change it right now is to edit the keyword lists (PHASE_KEYWORDS, STAGE_KEYWORDS, TASK_KEYWORDS, etc., near the top of generate-skills-json.py) and re-run make regen. There's no per-skill override and no in-UI tag editor yet.

Refreshing the data

Regenerate skills.json any time skills change, or any time a tag looks wrong after you've adjusted the keyword lists: 

cd ~/Sites/skills-explorer
make regen   # rebuild skills.json from ~/.agents/skills
make serve   # or: serve the site locally
# open http://localhost:8790

Or do both in one shot: make run.

Point at a different skills folder

SKILLS_ROOT=/some/other/path make regen
Note: This is a local-only tool with no scheduled or automatic rebuild. skills.json only reflects whatever was on disk the last time someone ran make regen — the page also force-bypasses browser cache on every load, so once you regenerate, a normal reload will always show the latest data. Requires Python 3.10+; no extra installs needed (standard library only).
