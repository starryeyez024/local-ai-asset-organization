A methodology for AI tooling hygiene

One Root, No Duplicates

A general approach for organizing AI agent skills and MCP servers so they have a single source of truth on disk, stay in sync across every tool that reads them, and never get silently duplicated, broken, or overwritten when something moves.

One physical root, symlinked everywhere

Summary

The whole approach in five moves

Move What it solves
1)Flatten One physical root, one entry per repo, named from the git remote — eliminates "which copy is real" and folder-name-vs-owner mismatches.
2)Symlink One canonical hub directory (e.g. ~/.agents/skills) holds the real per-repo symlinks; every other tool points a single symlink at that hub instead of rebuilding its own — moving or renaming touches symlinks only, never file contents. See the concrete directory checklist in the symlink fan-out section below for exactly which folders to check.
3)Split MCP Real code checkouts get a folder entry; doc-only servers get a lone file — and a stable indirection symlink absorbs future path changes for hardcoded configs.
4)Override safely Copy → edit → re-point instead of editing vendor/team skills in place, backed by a real, downloadable agent-facing safeguard skill as defense-in-depth (see below).
5)Match tooling to mechanism Know whether each tool discovers or is configured, and whether each installer copies or understands symlinks, before trusting it near the new layout.

The problem

AI assets sprawl across every tool you install

Once you use more than one AI coding tool, the same category of asset — a reusable skill, an MCP server checkout — ends up scattered across several tool-specific directories, each with its own installer, its own naming habits, and its own idea of where things should live.

In practice this shows up as a predictable list of symptoms:

The scattered starting point this methodology fixes

  • No single source of truth. The same skill might exist as a real directory in one tool's folder, a copy tracked by a different tool's own installer, and a symlink somewhere else — three different "current" versions with no way to tell which one is authoritative.
  • Symlinks that break on a move. A symlink points at an absolute path. Rename or relocate the folder it targets — even for an unrelated reason — and every symlink pointing at it silently goes dark. Nothing errors loudly; tools just stop finding the skill.
  • Finder-style aliases masquerading as symlinks. On macOS in particular, it's easy to end up with alias files instead of real symlinks (e.g. dragging a file with the wrong modifier key). They look identical in a folder listing, but no command-line tool or agent runtime follows them — they're dead weight that quietly never resolves.
  • Drift against git remotes. Several of these assets are git repositories with a real upstream remote. Once copies and symlinks are mixed together across tools, it becomes unclear which physical location is safe to git pull or edit, and which is a derived copy that will get silently overwritten or left stale.

None of this is caused by any one tool doing something wrong. It's the natural result of three or more independent tools (a general-purpose IDE agent, a terminal-based coding agent, a chat-style coding assistant) each shipping their own convention for "where skills live," with no shared layer underneath them.

The core decision

One flat physical root — every asset lives here, and only here

The fix is architectural, not procedural: pick exactly one folder on disk that is the real, physical home for every AI-related git repository you use — skills, MCP servers, all of it. Everywhere else a tool expects to find these assets becomes a symlink pointing back into this one root, never a second copy.

The rule, stated precisely

  • Flat, one level deep. No org sub-folders, no nested category/project structure. Every entry sits directly at the top level of the root.
  • One entry per repository, no exceptions. A repo containing twenty unrelated skills is still exactly one entry — all twenty stay nested inside it at their existing relative paths. A repo that is a single skill is also exactly one entry. There is no "is this a project repo or a skill-collection repo?" judgment call to make, because the answer never changes the outcome.
  • Named @org--repo-name. A literal double-dash separates the owning org/user from the repository name — not a real sub-folder, just a naming prefix a human can scan in a flat directory listing.

Illustrative flat root listing

~/AI Assets/ directory — every entry represents a git repo

@personal--writing-skills/          # a personal skill collection, several skills nested inside
@personal--utilities/               # no git remote — falls back to a personal-namespace prefix
@acme-team--internal-tools-cli/     # a team-owned repo, one flat entry regardless of size
@vendor-org--shared-skills-pack/    # a vendor/community repo, read-only by convention
@platform-org--build-automation/    # same repo as above — remote proved a different org (see case study)
@acme-team--docs-mcp.md              # doc-only MCP server — a lone FILE, not a folder
@vendor-org--example-mcp-server/    # MCP server WITH a real local code checkout

Because every repo is one entry with its internal layout left untouched, "where does this live" always has exactly one answer, and a two-line git status inside the root is enough to catch drift — no separate manifest file or audit script is needed to track what the flat structure already makes self-evident.

Why the naming convention matters

Name entries from the git remote, never from the local folder

The org prefix in @org--repo-name has to come from the repository's actual git remote -v output — never from assumptions, and never from whatever the local folder happened to be called before the migration. Local folder names are hints at best; they drift from reality more often than you'd expect.

Case study — the container folder lied

A repo sat inside a container folder implying it belonged to one team's namespace — call it team-a-tools/internal-tools-cli on disk. Running git remote -v against it resolved to an entirely different owner: git@example.com:platform-org/internal-tools-cli.git. The correct flat entry is @platform-org--internal-tools-cli, not @team-a-tools--internal-tools-cli — the local container folder's name reflected where someone happened to clone it, not who actually owns the code.

Case study — no .git at all

A folder that looked exactly like every other project — full of scripts and skill definitions — turned out to have no .git directory at all. git remote -v failed outright with "not a git repository." There's no remote to derive a name from, so the naming rule needs an explicit fallback: treat it as a personal, ungitted folder and prefix it with a default personal namespace (e.g. @personal--) rather than blocking the whole migration on "first go turn this into a real repo."

The general lesson: any naming scheme that derives identity from an external, verifiable source (the git remote) will occasionally disagree with local, human-assigned context (the folder it happened to be cloned into). Spot-check a meaningful sample before trusting the naming wholesale, and decide the fallback rule for "no remote exists" before you hit the first ungitted folder, not while migrating it.

The mechanism

Symlink fan-out: tool directories become pure views

Every AI tool still reads skills from wherever it natively expects to find them. What changes is that those tool-specific directories stop holding real files. In practice, only one directory does the real work — a canonical hub (e.g. ~/.agents/skills) holding one symlink per skill, pointing back into the flat root. Every other tool's directory becomes a single symlink pointing at that hub, not a second farm of its own.

Why not skip the root and put real files straight in the hub?

Because the two folders group things differently, and collapsing them breaks one grouping to satisfy the other. The physical root groups by repository — that's the git unit: one remote, one commit history, one git pull. The hub groups by individual skill — that's what a tool actually scans for. Most repos hold more than one skill, so a repo's name and any one skill's name inside it are usually different things. Put the real files directly in ~/.agents/skills and you either lose the repo-level grouping (git operations get harder to reason about) or lose the flat per-skill list a tool needs (nested skills stop being discoverable) — you can't have both in the same folder.

There's a second reason: ~/.agents/skills is one specific tool's own naming convention for where it looks, not a general storage standard. If your real, git-tracked files lived there directly, your canonical project storage would be coupled to that tool's implementation choice — replace or rename the tool later and your actual storage location's name no longer makes sense. Keeping the root separate and generically named keeps it independent of any single tool's convention: hub folders are cheap, disposable pointers; the physical root isn't. (The dot-prefix on ~/.agents isn't about hiding anything — it's the standard Unix convention for machine-facing config, the same category as .git or .ssh. The physical root is deliberately not dot-prefixed, because it's meant to be the plainly visible, human-browsable "real projects" location.)

Fan-out from the physical root to each tool

Physical root — real files live here, once ~/AI Assets/@org--repo-name/skills/<skill-name>/
The hub — e.g. ~/.agents/skills one symlink per skill canonical symlink farm

Nothing below the root line is ever a real file — only symlinks or native reads.

This is why the mechanism generalizes well: moving or renaming an asset only ever means updating where the symlinks point, never touching file contents. Once every other tool collapses its entire skill directory to one symlink pointing at the same canonical hub, that tool needs zero further maintenance when new skills are added — it inherits them automatically through the one symlink it already has.

Key property

A flat root plus a symlink layer turns an N-tools × M-skills maintenance problem into a one-time, M-sized setup. Adding a new tool later means pointing one new symlink at the existing hub, not re-copying every existing skill again.

MCP servers

Two kinds of MCP server need two different treatments

MCP servers aren't discovered by directory-scanning the way skills are. Every tool's MCP config file has an explicit, named block pointing at either a local command to launch or a remote URL to call — so "symlinking an MCP server" means something narrower than it does for skills, and it splits into two distinct cases.

Real local code checkout

If the MCP server is a project you actually cloned — source code, a virtual environment, a launch script — it gets a normal flat physical entry in the root, the same as any other repo (@vendor-org--example-mcp-server/). There's real code to move and real internal structure to preserve.

Documentation-only / vendor-hosted

If the server is a remote URL, or a globally-installed binary launched from PATH, there's no local code to move at all — only setup notes worth keeping close by. That case gets a lone symlinked markdown file sitting directly at the root's top level (@acme-team--docs-mcp.md), not a folder. Wrapping one file in a folder that will never hold a second file is pure ceremony; a bare file is a more honest representation of "there's nothing here but notes."

Because config files hardcode a path rather than scanning a directory, the stable-symlink layer matters more for MCP servers than it does for skills, not less. A skill's tool-facing directory can silently absorb a rename because the tool re-scans it. An MCP config's command/args fields do not re-scan anything — they only re-resolve at launch time, so a moved or renamed real checkout breaks every config file that hardcodes the old path until each one is edited by hand.

The fix is one extra layer of indirection: a small set of stable-path symlinks (grouped separately from the skill symlinks) that every config file references instead of the real checkout path directly. If the physical root ever reorganizes again, exactly one symlink target needs updating per server — not every config file that mentions it.

The override problem

Never edit a vendor or team skill in place

The moment you tweak a skill you don't own — a team-shared skill, a vendor's published one — directly inside its source repository, you've created uncommitted drift in a checkout other people also rely on. The next git pull either conflicts or silently discards your edit. The fix is a small, repeatable procedure instead of a habit to remember.

Copy → edit → re-point

  1. Copy the whole skill folder — not just its main definition file, but every supporting script, asset, and reference inside it — into a dedicated overrides area of the physical root, mirroring the original's internal path.
  2. Make the requested edit in the copy. The original, upstream-owned folder is never touched.
  3. Re-point the one tool-facing symlink for that skill's name at the new override location instead of the original. Because tool directories are already collapsed to a single symlink layer, this is one symlink update, not one per tool.

Concrete example: a skill after being overridden

~/AI Assets/ — vendor original untouched, override copy added alongside it

@org-a--fiddlewidget/
@personal--fiddlewidget/
└── skills/
    └── fiddlewidget/
        └── SKILL.md

~/.agents/skills/ — the tool-facing symlink re-pointed off the vendor copy

fiddlewidget               → ~/AI Assets/@personal--fiddlewidget/skills/fiddlewidget/

This is the override case, not a new pattern. The vendor's original, @org-a--fiddlewidget/, stays on disk exactly as published — untouched, and still worth keeping around for future diffing against upstream updates. The hub symlink no longer points at it: after the copy → edit → re-point steps above, it points at @personal--fiddlewidget/skills/fiddlewidget/ instead, the edited copy. Same flat-root-plus-hub mechanism as the diagrams earlier in this section — the only difference here is that two physical copies of the same skill name now exist side by side, and the symlink picks which one is "live."

Skill-override-safeguard: an agent-facing guardrail

Because this procedure depends on remembering to follow it every single time, it can be encoded as a standing instruction file that any agent reads before editing a skill — this exists as a real, working skill named skill-override-safeguard, not just a description of an idea. Its job: whenever an agent is asked to edit or modify a skill that lives outside the designated overrides area, it must stop, run the copy → edit → re-point procedure above instead, and never touch the original in place.

This is a defense-in-depth layer, not a hard guarantee. There is no OS-level permission lock and no technical enforcement — it works only if the agent actually consults the safeguard skill before editing. A determined or simply confused agent that skips it can still edit the original directly, exactly as before. Treat it as one layer alongside others (like periodically checking git status in vendor-owned checkouts to catch drift that slipped through anyway), not a replacement for them.

General lessons

What this reveals about tool behavior more broadly

Copy-based installers and symlinks don't mix safely by default

Many skill/package installers are fundamentally copy-based: installing means writing a fresh copy of the source into the destination directory, with no concept of "this destination is already a symlink to something else." If you've replaced an installed copy with a symlink back to your own source checkout — a reasonable thing to do once you're managing a flat root — a naive copy-based installer can do one of two bad things: silently skip the write and report success anyway (leaving you with stale content and false confidence), or write straight through the symlink and corrupt the file back at the symlink's real target.

The safe behavior an installer should have is to detect that its destination is a symlink and treat that as an explicit conflict requiring confirmation, then unlink and replace the symlink outright rather than writing through it. If a tool you depend on doesn't do this, verify its behavior in a throwaway test before trusting it against a symlinked destination for real.

Discovery mechanism determines how much a stable-path layer matters

Skills are typically discovered — a tool scans a known directory and picks up whatever's there, symlink or not, so a rename mostly self-heals the moment the tool re-scans. MCP servers are typically configured — an explicit path or command sits hardcoded in a config file that is read once at connection time and never re-scanned. That difference is why a stable indirection symlink is optional convenience for skills but load-bearing for MCP servers: without it, every reorganization of the physical root means editing every config file that references an MCP server's old path by hand, across every tool that has its own separate config file.

The pattern worth generalizing

Whenever a single logical asset needs to be visible to several independent tools, ask two questions before designing the sync: (1) does each tool discover the asset by scanning a directory, or does it require an explicit, hardcoded reference to it, and (2) does whatever writes to that asset understand symlinks, or does it only know how to copy? The answers determine whether one flat root and a thin symlink layer is sufficient, or whether you also need a stable indirection point and careful handling around any copy-based tooling in the mix.

AI-asset-auditor: putting this methodology into practice

Working out the discovery-vs-configured and copy-vs-symlink questions above by hand, repo by repo, is exactly the kind of repeatable audit that's easy to get wrong under time pressure — this exists as a real, working skill named ai-asset-auditor, not just a description of an idea. Its job: scan your tool-specific directories for the symptoms this page describes — duplicated skills, dead symlinks, Finder aliases masquerading as symlinks, git remotes that no longer match local folder names — and propose a flat-root migration plan.

It runs discover-then-confirm: it always presents its plan and asks clarifying questions before touching any file, and never executes a move, rename, delete, or symlink change without explicit per-plan confirmation. Treat it as the operational counterpart to the methodology on this page, not a substitute for reading it.
