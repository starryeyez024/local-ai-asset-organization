Guide 2 · Physical organization

Organize the assets once, then deliver them safely

A physical root gives real files a clear home. Tool-facing directories are views or adapters, not competing sources of truth.

Physical root

Derive identity from the repository

Organize checkouts by the git remote owner, complete subgroup path, and repository name. Lowercase every path segment so the local structure remains predictable.

Physical root vs. tool-facing symlink views

Identity rule: preserve nested remote groups. If a remote owner is RHEcosystemAppEng, use rhecosystemappeng/ locally, not a mixed-case variant.

Tool-facing views

One name, one active delivery path

A symlink hub can make local discovery convenient, but it is only one delivery mechanism. Some tools follow links, some runtimes require committed files, and hosted agents may need a plugin or synced copy.

Delivery mechanismUse whenRisk to manage
SymlinkA local tool has been tested to follow the link.Broken targets, unsupported discovery, remote/cloud isolation.
Committed fileA team or hosted runtime must receive the asset with the project.Drift if it is copied from another source without an update rule.
Generated copyA tool requires a different package shape or native wrapper.Unclear ownership; document the canonical source and regeneration command.
Native/platform configurationThe tool owns settings, MCP connections, memory, or plugins.Configuration may not be portable or visible in the repository.

Collisions

Never let duplicate names choose silently

Two repositories may ship a skill with the same folder or frontmatter name. Do not overwrite an existing tool-facing entry without confirmation.

  1. Show the existing target and the proposed target.
  2. Prefer a unique or organization-prefixed name if both skills need to remain active.
  3. If one is an intentional override, record the canonical source and re-point the one active delivery path.
  4. When precedence is undocumented, test the actual tool rather than assuming project wins over global.
Safe default: one active skill name per tool-facing namespace. Duplicates should be deliberate, visible, and explainable.

Overrides

Copy → edit → re-point

Never edit a vendor or team skill directly inside its shared checkout. A pull or package update can overwrite the change and leave untracked drift.

1. Copy

Copy the whole skill folder into your personal namespace, including scripts, references, and assets.

2. Edit

Make the change in the personal copy and keep the upstream checkout clean.

3. Re-point

Point the tool-facing entry at the personal copy. Keep the original name when the override is intentional.

~/AI Assets/vendor-org/repo/skills/fiddlewidget/
~/AI Assets/your-username/fiddlewidget/             # edited copy

~/.agents/skills/fiddlewidget →
  ~/AI Assets/your-username/fiddlewidget/

Audit before action

Read first, then propose a change

  1. Discover skills, MCP configuration, symlinks, aliases, and git remotes read-only.
  2. Flag duplicates, broken targets, real copies, and unsupported layouts.
  3. Present the full plan, including every move, copy, delete, or link change.
  4. Ask for confirmation before changing the filesystem.

Use the ai-asset-auditor for this workflow and the skill-linker for selective local links.

Bootstrap and configuration

Let native files point to the shared setup

A tool-native CLAUDE.md can point Claude Code to the canonical AGENTS.md. The TOML file belongs beside the canonical instructions as machine configuration; it gives scripts and setup helpers a stable place to read paths, but Claude Code does not automatically interpret arbitrary TOML as instructions.

Claude bootstrap

# ~/.claude/CLAUDE.md
Read and follow:
  ~/.config/ai-tools/AGENTS.md

Use machine paths from:
  ~/.config/ai-tools/ai-tools.toml

Canonical machine configuration

# ~/.config/ai-tools/ai-tools.toml
[directories]
install_dir = "/absolute/path/to/AI Assets"
symlinks_dir = "/absolute/path/to/.agents/skills"
Important: the example uses the repository’s actual configuration keys. Treat the TOML as a contract for your scripts and adapters; keep private paths, credentials, and personal context out of a shareable repository.
