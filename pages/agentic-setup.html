Guide 1 · Setup model

Separate instructions, configuration, and context

The setup skill prepares a private home for these files and connects your tools to it. It checks what you already have and asks for your input as it goes.

Setup files

What goes in each file

You can start the setup conversation before preparing any files. These examples explain what the assistant will create or adapt for you.

Instructions

Rules for how an agent should work safely, communicate, check quality, and choose which sources to trust.

In your private repo:
AGENTS.md.

Configuration

Paths and tool settings for this machine, including project scope, MCP endpoints, and references to credentials.

In your private repo:
agent-config.toml.

Context

Knowledge about a person, team, or project that an agent can consult when relevant.

In your private repo:
personal-context/, with small files you can maintain over time.

How they connect: AGENTS.md says when to consult context. agent-config.toml gives local workflows a path to it. The context files provide the details.

Your private repository

One home for your personal agent setup

For a new setup, the skill recommends keeping your global instructions, local configuration, and personal context in a private Git repository at ~/.config/agent-tools/. It inspects your configuration and skill locations, asks about any gaps, and recommends paths before creating files. It then configures each tool to read the shared files; agents do not discover this folder automatically. OpenCode’s global config location is one precedent for an application-specific folder under ~/.config/.

~/.config/agent-tools/       # private Git repository
├── AGENTS.md                # global instructions
├── agent-config.toml        # local paths and settings
├── personal-context/        # maintained context
    ├── communication-style.md
    ├── current-projects.md
    ├── decision-log.md
    └── ...                     # other useful topics
├── README.md                # recovery notes
└── .gitignore               # local output to exclude

~/.codex/AGENTS.md          # short Codex bootstrap
~/.claude/CLAUDE.md         # short Claude bootstrap

The assistant keeps each tool’s instruction file short and points it to the repo. Cursor User Rules and ChatGPT Project settings are configured in those products; if it cannot access a setting, it gives you the exact text and action needed. A matching filename is not enough for discovery: adding a CODEX.md would not make Codex load it.

Personal context

Let your assistant interview you

You don’t need to write a profile from scratch. The setup skill asks a few questions about your work, drafts a short context file, and asks you to correct it. It can start from notes you already keep.

The assistant starts with who you are, what you’re responsible for, and what makes an answer useful to you. It suggests adding projects, communication preferences, goals, or domain knowledge when they matter. You can stop after the first useful files and come back for more.

Describe how you actually work. Correct anything the draft gets wrong. The assistant saves the approved files privately, tells your tools when to read them, and tries a task with you to check that the context helps.

Later, just ask: “Update my context: my priorities have changed,” or “Continue the personal context interview.”

Context placement

Keep useful context close to your setup

Keeping personal-context/ beside your instructions and configuration lets you find, update, and back up the files together, with or without a notes app. If you already maintain context elsewhere, the assistant can use that location instead of moving it.

The setup skill writes instructions telling local agents when to consult context and which files a task needs. Loading the whole folder every time is unnecessary. Hosted agents need selected context through their platform’s supported projects, files, or connections; the assistant helps prepare that connection because a laptop path alone is not enough.

Scope

Where the settings apply

The assistant checks whether a setting belongs to your personal setup, a shared project, or a platform. If the choice affects who receives your instructions or context, it explains the options before changing it.

Path rules

How the assistant chooses paths

The skill resolves paths for your machine and checks that each tool can read them. These conventions explain the paths you’ll see in its proposed configuration.

  • Cross-tool configuration: use an absolute path such as /Users/alex/AI Assets.
  • Files inside a known root: use a relative path such as projects/current.md.
  • Shareable repositories: use placeholders or repository-relative paths; never commit a maintainer’s private machine path.
  • Hosted runtimes: assume local absolute paths and local symlinks are unavailable unless the platform explicitly syncs them.
Project rule: a project-level file only works when the consuming tool recognizes that filename, path, and asset type. “Project overrides global” is not a universal rule.

Machine configuration

What belongs in agent-config.toml

The setup skill creates or updates this file and connects the instruction and context paths to your tools. The linker and Explorer read the same skills folder, so linked skills appear when the assistant refreshes your catalog. This example shows the recommended starting configuration.

# ~/.config/agent-tools/agent-config.toml
[directories]
install_dir = "~/AI Assets"
symlinks_dir = "~/.agents/skills"
context_root = "~/.config/agent-tools/personal-context"

[instructions]
shared_file = "~/.config/agent-tools/AGENTS.md"

~ means your home directory; the linker and Explorer expand it automatically. These paths match the recommended layout: repositories in ~/AI Assets/, skill links in ~/.agents/skills/, and personal setup files in ~/.config/agent-tools/. The assistant checks other scripts and tool instruction files that depend on these paths. If you use more than one computer, it helps keep each machine’s path settings separate and selects the active set locally.

Keep this repository private: it may contain personal context and machine paths. Keep credentials in a secret store, outside Git.
