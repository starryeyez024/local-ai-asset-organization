Guide 1 · Setup model

Separate instructions, configuration, and context

Keep these files in a place you maintain, then use each tool’s settings or instruction files to point to them.

Setup files

What goes in each file

Instructions

Rules for how an agent should work safely, communicate, check quality, and choose which sources to trust.

In your private repo:
AGENTS.md.

Configuration

Paths and tool settings for this machine, including project scope, MCP endpoints, and references to credentials.

In your private repo:
agent-config.toml.

Context

Knowledge about a person, team, or project that an agent can consult when relevant.

In your private repo:
personal-context/, with small files you can maintain over time.

How they connect: AGENTS.md says when to consult context. agent-config.toml gives local workflows a path to it. The context files provide the details.

Your private repository

One home for your personal agent setup

Keep your global instructions, local configuration, and personal context together in a private Git repository at ~/.config/agent-tools/. This is a location you choose and connect to each tool; agents do not automatically discover it. OpenCode’s global config location is one precedent for an application-specific folder under ~/.config/.

~/.config/agent-tools/       # private Git repository
├── AGENTS.md                # global instructions
├── agent-config.toml        # local paths and settings
├── personal-context/        # maintained context
    ├── communication-style.md
    ├── current-projects.md
    ├── decision-log.md
    └── ...                     # other useful topics
├── README.md                # recovery notes
└── .gitignore               # local output to exclude

~/.codex/AGENTS.md          # short Codex bootstrap
~/.claude/CLAUDE.md         # short Claude bootstrap

Keep each tool’s instruction file short and point it to the repo. Configure Cursor User Rules and ChatGPT Project settings in those products. A matching filename is not enough for discovery, so do not create a CODEX.md just to match the other tools.

Personal context

Let your assistant interview you

You don’t need to write a profile from scratch. The setup skill asks a few questions about your work, drafts a short context file, and asks you to correct it. It can start from notes you already keep.

Begin with who you are, what you’re responsible for, and what makes an answer useful to you. Add projects, communication preferences, goals, or domain knowledge when they matter. You can stop after the first useful files and come back for more.

Describe how you actually work. Correct anything the draft gets wrong. The assistant saves the approved files privately, tells your tools when to read them, and tries a task with you to check that the context helps.

Later, just ask: “Update my context: my priorities have changed,” or “Continue the personal context interview.”

Context placement

Keep useful context close to your setup

Keeping personal-context/ beside your instructions and configuration lets you find, update, and back up the files together, with or without a notes app. If you already maintain context elsewhere, point to that location.

Tell local agents when to consult context and which files a task needs. Loading the whole folder every time is unnecessary. Supply context to hosted agents through their platform’s supported projects, files, or connections; they cannot use a laptop path alone.

Scope

Choose where the settings apply

ScopeUse it forSharing rule
Global / userPersonal defaults, local skills, personal preferences, and machine-only configuration.Local convenience. Do not assume a hosted agent can see it.
Project / repositoryInstructions, skills, and context that should travel with a codebase or team project.Commit real files when teammates or cloud agents need them.
Nested projectGuidance that applies only to a subdirectory or component.Use only when the tool supports nested discovery and precedence.
Platform workspaceChatGPT Projects, plugins, shared skills, connected apps, and hosted MCP configuration.Configure through the platform; filesystem links do not apply.

Path rules

Use absolute paths across tools and relative paths inside roots

  • Cross-tool configuration: use an absolute path such as /Users/alex/AI Assets.
  • Files inside a known root: use a relative path such as projects/current.md.
  • Shareable repositories: use placeholders or repository-relative paths; never commit a maintainer’s private machine path.
  • Hosted runtimes: assume local absolute paths and local symlinks are unavailable unless the platform explicitly syncs them.
Project rule: a project-level file only works when the consuming tool recognizes that filename, path, and asset type. “Project overrides global” is not a universal rule.

Machine configuration

What belongs in agent-config.toml

The skill linker reads the repository root and skills folder from this file. The Explorer uses the same skills folder, so linked skills appear when you regenerate the catalog. Use the instruction and context paths in your agent’s setup instructions.

# ~/.config/agent-tools/agent-config.toml
[directories]
install_dir = "~/AI Assets"
symlinks_dir = "~/.agents/skills"
context_root = "~/.config/agent-tools/personal-context"

[instructions]
shared_file = "~/.config/agent-tools/AGENTS.md"

~ means your home directory; the linker and Explorer expand it automatically. These paths match the recommended layout: repositories in ~/AI Assets/, skill links in ~/.agents/skills/, and personal setup files in ~/.config/agent-tools/. Connect any other scripts and tool instruction files to the paths they need. If you use more than one computer, keep separate non-secret path settings for each and select the active set locally.

Keep this repository private: it may contain personal context and machine paths. Keep credentials in a secret store, outside Git.
