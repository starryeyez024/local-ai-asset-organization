Guide 1 · Setup model

Separate instructions, configuration, and context

A reliable agentic workspace gives each concern one clear home and lets tool-native bootstraps point back to the canonical sources.

The three concerns

Keep behavior, paths, and knowledge distinct

Instructions

Rules for how an agent should behave: safety, quality, communication, and source-of-truth conventions.

Canonical form: one global AGENTS.md or equivalent.

Configuration

Machine-specific paths, tool settings, project scope, MCP endpoints, and credentials references.

Canonical form: one machine configuration file; never a skill’s private copy.

Context

Information about a person, organization, project, domain, or working style.

Canonical form: a separate context portfolio or project knowledge base.

Why separate them? Instructions tell agents how to act. Configuration tells tools where things are. Context helps agents understand the work. Mixing them creates portability and precedence problems.

Instruction hierarchy

Use short native bootstraps, not parallel copies

A neutral user-level location can hold the canonical global files. Each tool can retain the filename it natively discovers, but that file should be a short pointer or tool-specific adapter rather than a second full copy of the rules.

~/.config/ai-tools/
├── AGENTS.md              # canonical global behavior
└── ai-tools.toml          # canonical machine configuration

~/.codex/AGENTS.md          # short Codex bootstrap
~/.claude/CLAUDE.md         # Claude-specific bootstrap/context
Cursor User Rules           # native settings surface
ChatGPT Project settings    # platform-managed instructions

Do not create a CODEX.md merely to make filenames look symmetrical. Use the native convention the tool actually discovers.

Scope

Global and project layers are not interchangeable

ScopeUse it forSharing rule
Global / userPersonal defaults, local skills, personal preferences, and machine-only configuration.Local convenience. Do not assume a hosted agent can see it.
Project / repositoryInstructions, skills, and context that should travel with a codebase or team project.Commit real files when teammates or cloud agents need them.
Nested projectGuidance that applies only to a subdirectory or component.Use only when the tool supports nested discovery and precedence.
Platform workspaceChatGPT Projects, plugins, shared skills, connected apps, and hosted MCP configuration.Configure through the platform; filesystem links do not apply.

Path rules

Use absolute paths across tools and relative paths inside roots

  • Cross-tool configuration: use an absolute path such as /absolute/path/to/asset-root.
  • Files inside a known root: use a relative path such as 08-Local setup/.
  • Shareable repositories: use placeholders or repository-relative paths; never commit a maintainer’s private machine path.
  • Hosted runtimes: assume local absolute paths and local symlinks are unavailable unless the platform explicitly syncs them.
Project rule: a project-level file only works when the consuming tool recognizes that filename, path, and asset type. “Project overrides global” is not a universal rule.

Machine configuration

What belongs in ai-tools.toml

This file is the canonical map for local setup scripts and adapters. It tells automation where the physical asset root, tool-facing skills hub, shared instructions, and optional knowledge vault live. It is not itself an instruction file, and agents do not automatically interpret arbitrary TOML.

# ~/.config/ai-tools/ai-tools.toml
[directories]
install_dir = "/absolute/path/to/AI Assets"
symlinks_dir = "/absolute/path/to/.agents/skills"
vault_root = "/absolute/path/to/knowledge-vault"

[instructions]
shared_file = "/absolute/path/to/AGENTS.md"
  • install_dir: the physical root where repositories and real asset files live.
  • symlinks_dir: the local tool-facing skills hub, when symlinks are supported.
  • vault_root: an optional durable knowledge location used by your workflows.
  • shared_file: the canonical global behavior-instructions file that native bootstraps can reference.
Use absolute paths: TOML does not expand ~ by itself. Never commit private machine paths, credentials, or personal context to a shareable repository.

Portable setup sequence

Build the pattern once

  1. Create a neutral user-level configuration directory.
  2. Put the canonical global instruction file and machine configuration there.
  3. Add each tool’s short native bootstrap or adapter.
  4. Keep portable context in a separate portfolio or repository.
  5. Commit project-level instructions and skills when the project or cloud runtime needs them.
  6. Test the setup from each relevant working directory and runtime.
Shareable project rule: publish methodology, examples, templates, and safe workflows. Do not publish private context, credentials, or machine-specific configuration.
