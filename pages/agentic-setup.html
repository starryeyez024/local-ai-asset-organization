Guide 1 · Setup model

Separate instructions, configuration, and context

A reliable agentic workspace gives each concern one clear home and lets tool-native bootstraps point back to the canonical sources.

The three concerns

Keep behavior, paths, and knowledge distinct

Instructions

Rules for how an agent should behave: safety, quality, communication, and source-of-truth conventions.

In the proposed repo:
AGENTS.md.

Configuration

Machine-specific paths, tool settings, project scope, MCP endpoints, and credentials references.

In the proposed repo:
agent-config.toml.

Context

Knowledge about a person, team, or project that an agent can consult when relevant.

In the proposed repo:
personal-context/, with small files you can maintain over time.

How they connect: AGENTS.md says when to consult context. agent-config.toml gives local workflows a path to it. The context files provide the details.

Proposed private repository

One home for your personal agent setup

Keep your global instructions, local configuration, and personal context together in a private Git repository at ~/.config/agent-tools/. This is a location you choose and connect to each tool; agents do not automatically discover it. OpenCode’s global config location is one precedent for an application-specific folder under ~/.config/.

~/.config/agent-tools/       # private Git repository
├── AGENTS.md                # global instructions
├── agent-config.toml        # local paths and settings
├── personal-context/        # maintained context
    ├── communication-style.md
    ├── current-projects.md
    ├── decision-log.md
    └── ...                     # other useful topics
├── README.md                # recovery notes
└── .gitignore               # local output to exclude

~/.codex/AGENTS.md          # short Codex bootstrap
~/.claude/CLAUDE.md         # short Claude bootstrap

Keep tool-native instruction files as short pointers or adapters to the repo, rather than second full copies. Cursor User Rules and ChatGPT Project settings live in their products; use those surfaces instead of inventing a file path. Do not create a CODEX.md merely for symmetry.

Context placement

Keep useful context close to your setup

The example keeps personal-context/ beside your instructions and configuration, so the files are easy to find, update, and back up together. This works without a notes app. If you already maintain context elsewhere, keep that source and point your setup to it.

Tell local agents when to consult context, and have them read the files relevant to the task rather than loading the whole folder every time. Hosted agents need the relevant files supplied through their platform’s supported projects, files, or connections; a laptop path alone is not available to them.

Scope

Global and project layers are not interchangeable

ScopeUse it forSharing rule
Global / userPersonal defaults, local skills, personal preferences, and machine-only configuration.Local convenience. Do not assume a hosted agent can see it.
Project / repositoryInstructions, skills, and context that should travel with a codebase or team project.Commit real files when teammates or cloud agents need them.
Nested projectGuidance that applies only to a subdirectory or component.Use only when the tool supports nested discovery and precedence.
Platform workspaceChatGPT Projects, plugins, shared skills, connected apps, and hosted MCP configuration.Configure through the platform; filesystem links do not apply.

Path rules

Use absolute paths across tools and relative paths inside roots

  • Cross-tool configuration: use an absolute path such as /absolute/path/to/asset-root.
  • Files inside a known root: use a relative path such as projects/current.md.
  • Shareable repositories: use placeholders or repository-relative paths; never commit a maintainer’s private machine path.
  • Hosted runtimes: assume local absolute paths and local symlinks are unavailable unless the platform explicitly syncs them.
Project rule: a project-level file only works when the consuming tool recognizes that filename, path, and asset type. “Project overrides global” is not a universal rule.

Machine configuration

What belongs in agent-config.toml

This proposed file maps local setup scripts and adapters to the asset root, skills folder, shared instructions, and personal context. Agents do not automatically interpret arbitrary TOML; the workflows that use this file must be configured to read it.

# ~/.config/agent-tools/agent-config.toml
[directories]
install_dir = "/absolute/path/to/AI Assets"
symlinks_dir = "/absolute/path/to/.agents/skills"
context_root = "/absolute/path/to/.config/agent-tools/personal-context" # example for workflows you configure

[instructions]
shared_file = "/absolute/path/to/.config/agent-tools/AGENTS.md"

Replace /absolute/path/to with your home directory’s absolute path. The keys are examples: use the names your scripts actually read. Existing scripts and native bootstraps need to be updated before relying on the new folder and filename. If you use more than one computer, keep separate non-secret path settings for each and select the active set locally.

Keep this repository private: it may contain personal context and machine paths. TOML does not expand ~ by itself. Keep credentials in a secret store, outside Git.

Portable setup sequence

Build the pattern once

  1. Create a private Git repository at ~/.config/agent-tools/.
  2. Add AGENTS.md, agent-config.toml, and a personal-context/ folder with only the context you want agents to use. Add a short README.md for recovery and a .gitignore for local output.
  3. Optionally back it up to a private remote after reviewing the files; local Git history alone is not an off-device backup.
  4. Update each local workflow to read the new configuration path, then add each tool’s short native bootstrap or adapter.
  5. Give hosted tools relevant context through their supported files, projects, or connections.
  6. Commit project-level instructions and skills when the project or cloud runtime needs them.
  7. Test the setup from each relevant working directory and runtime.
Shareable project rule: publish methodology, examples, templates, and safe workflows. Keep the personal setup repo private, and keep credentials out of it.
