The problem

Problem #1: the same asset ends up in several places

As you use more than one AI coding tool, or installer (Lola, NPX, Git, Marketplaces, etc), your skills and MCP servers can end up spread across different folders. Each installer and runtime sees a different slice of that setup.

Why is this a problem?

  • Unclear ownership: a skill may be a tracked folder in one repository, a copied install in another tool, and a symlink elsewhere. It becomes hard to know which version to edit or update.
  • Overwritten customization: local tweaks to an installed skill can disappear when its vendor or package manager refreshes it.
  • Runtime mismatch: a local path or symlink does not automatically travel with a project or become available to a hosted agent.

These problems grow from several tools having different discovery and delivery rules. The goal is to make the source of each asset clear, then deliver it through the path each tool actually supports.

What the model changes

Clear source locations

Keep skills and code in tracked repositories, with personal instructions, configuration, and context in a separate private repo.

Verified delivery

Use a symlink, committed file, generated copy, native configuration, or platform-managed package according to the consuming tool.

Documented exceptions

Allow intentional duplication when a tool or runtime cannot consume the canonical representation safely.

Five principles

A simple operating model

  1. Separate concerns: instructions, configuration, and context are different things.
  2. Keep one canonical source: portable content should have a clear owner and update path.
  3. Choose the right delivery mechanism: symlink, committed file, generated copy, native config, or platform package.
  4. Override safely: copy → edit → re-point instead of modifying vendor or team assets in place.
  5. Verify before automating: discovery, precedence, installers, and hosted runtimes differ.

Getting started

Audit first, then change with confirmation

  1. Inventory current skills, instructions, MCP configurations, and runtime targets.
  2. Identify canonical sources and any existing copies or symlink views.
  3. Start with the tool and asset you plan to change. Use the relevant part of the compatibility guide when its path, scope, or runtime is unclear.
  4. Use the ai-asset-auditor for a read-first migration plan.
  5. Make filesystem changes only after reviewing and confirming the plan.
