One source, different delivery mechanisms

Use this matrix before creating a symlink or assuming a project-level override will work. The correct answer depends on the asset, agent, scope, and runtime.

Legend

How to read the matrix

Symlink

The tool follows the canonical local folder. Test this before relying on it.

Committed

A real file travels with a shared repository and is available to compatible hosted runtimes.

Generated / native

A copy, wrapper, native config, plugin, or platform-managed package delivers the content in the required shape.

Runtime labels: Local means the machine where the files live. Project means committed with the repository. Cloud means explicitly synced or packaged for a hosted agent. Verify means version, runtime, or configuration can change the result.

Project scope

Project-level files are not universal overrides

A project-level asset works only when the tool recognizes that asset type and path. For a shared repository, prefer real committed files. Use local symlinks only where the target tool has been tested to follow them.

  1. Commit project skills, instructions, rules, and context when teammates or hosted agents need them.
  2. Keep MCP configuration tool-native and free of secrets.
  3. Use generated copies when the target tool requires a different structure.
  4. Document the canonical source and refresh method for every copy.

Precedence and collisions

Project directory overrides

A project-level file only changes behavior when the tool recognizes that asset type at that project path and its documented precedence rules allow the project scope to override or supplement the global scope. A project file cannot override a setting owned by the desktop app, a plugin, or another tool.
