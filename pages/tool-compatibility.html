Verify a migration

How the assistant verifies the setup

During guided setup, the assistant performs these checks and reports the results before proposing retirement of an old path. It asks for your input when a conflict or change needs your judgment.

  1. It checks the tool’s skill roots and installed plugins from the intended project, noting duplicates, package versions, and installation scopes.
  2. It keeps maintained repository skills at their source and lets marketplace installers manage their packages.
  3. It uses a supported link, native setting, or package installation, then confirms discovery and tries a representative invocation in that runtime.
  4. Before removing an approved obsolete link or installation, it checks that the replacement works and that other tools no longer need the old one.

Testing one link leaves the rest of the migration unverified. Instructions to “watch” a folder do not change where a tool looks for skills. Some tools continue to scan their built-in roots.

How to read the matrix

Symlink

The tool follows a link to the source folder. The assistant checks that it can read the linked files.

Committed

The file travels with the repository, so compatible hosted runtimes can read it.

Generated / native

The tool receives the format it needs through a copy, wrapper, native config, plugin, or platform-managed package.

Runtime labels: Local means the machine where the files live. Project means committed with the repository. Cloud means explicitly synced or packaged for a hosted agent. Verify means version, runtime, or configuration can change the result.

Managed packages

Check whether the installed package works here

The assistant checks the installer’s inventory, then verifies that the intended runtime enables, discovers, and successfully invokes the plugin. A cache folder alone proves none of those. It runs these checks from the relevant project: a project-scoped plugin may be enabled there and inactive elsewhere.

The assistant keeps managed files under their installer’s control and checks loose skills and links for overlap, preserving shared sources that other tools need. A plugin loaded from a local skills directory may be repository-managed rather than marketplace-installed.

For example, Claude Code namespaces plugin skills as /plugin-name:skill-name, so a plugin and a same-name loose skill can coexist. See skill name resolution and plugin scopes and management.

Project scope

Check which project files the tool recognizes

The tool must recognize the project file’s type and path. The assistant checks these requirements when preparing project files; commits and publishing remain subject to your approval.

  1. Shared skills, instructions, rules, and context need real files that can travel with the repository.
  2. MCP configuration uses the tool’s native format and keeps secrets outside the repository.
  3. A generated copy may be needed when the target tool requires a different structure.
  4. Each copy needs a recorded source and refresh method.

Precedence and collisions

Project directory overrides

Once the tool recognizes a project file, its precedence rules determine whether that file overrides or adds to global settings. Project files cannot override settings owned by a desktop app, plugin, or another tool.

Scripts and executable helpers

Resolve names through explicit desktop instructions

Scripts stay in their owning repository or skill bundle. A shared private catalog maps a registered name to its file and invocation details. The setup assistant connects a short lookup rule through each app's supported instructions and verifies a harmless script by name from another working directory. This local convention assumes the agent already has permission to run the requested script; it does not create a native ~/.agents/scripts discovery path.
